## 개요

OpenClaw v2026.6.11이 2026년 6월 30일 정식 공개됐습니다. 이번 릴리즈는 큰 신기능을 얹는 쪽보다는, 그동안 "왠지 미덥지 않았던" 구석을 하나하나 조이는 쪽입니다. 답장이 엉뚱한 대화로 튀거나, 전송이 멈춰 보이거나, 재접속 뒤 흐름이 끊기거나, 모델 세팅이 알 수 없는 이유로 실패하던 상황을 광범위하게 손봤습니다. 관리자 쪽 기본값도 안전한 방향으로 살짝 옮겨왔습니다.

## 핵심 요약

- **채널 전달 신뢰성 전면 정비**: 텔레그램·왓츠앱·매트릭스·구글 챗·아이메시지·페이슈·매터모스트·웹챗·컨트롤 UI·터미널 UI에 걸쳐 답장 라우팅과 재접속 처리가 촘촘해졌습니다.
- **프로바이더·모델 복구력 강화**: MiniMax TTS 오디오 포맷 명시, 게이트웨이 로그의 프로바이더·모델 상태 노출 복구, 캐시 경계 마커 누출 차단, Gemini 스키마 호환 등이 함께 들어갔습니다.
- **세션·메모리·신뢰 연속성**: OpenAI Responses 히스토리가 불완전해져도 다음 턴이 살아나고, Codex 대용량 툴 출력이 잘리지 않고, 컨트롤 UI 대화가 슬립·재접속 뒤에도 유지됩니다.
- **Slack 라우터 릴레이 모드 신규**: 관리형·다중 게이트웨이 환경에서 Slack 트래픽을 중앙에서 정리하면서도 각 게이트웨이의 소유권은 유지합니다.
- **Raft External Agent 웨이크 브리지**: 로컬 CLI로 워크스페이스에 밀린 작업이 있을 때 에이전트를 깨울 수 있습니다.
- **공식 플러그인 설치·복구 개선**: `plugins.allow` 오탐 진단, 신뢰 경고에 복사 가능한 예시 명령, `npm EOVERRIDE` 회복, 관리형 의존성 pin 정리가 정상 흐름으로 편입됐습니다.

## 본문

### 채널 전달을 진짜로 믿을 수 있게

이번 릴리즈의 헤드라인은 채널입니다. 다양한 곳에서 "답이 엉뚱한 대화로 갔다"는 리포트를 봤다면, 6.11 이후에 다시 확인해 볼 만합니다. 구글 챗의 새 DM이 그룹 대화처럼 처리되던 문제가 잡혔고, 텔레그램에서는 사용자가 봇의 예전 메시지를 인용해도 최신 질문 흐름을 놓치지 않습니다. 왓츠앱 그룹 대화의 컨텍스트도 재시도·재접속·그룹 이동 상황에서 안정적으로 이어집니다.

아이메시지는 명령과 링크가 함께 온 메시지를 지연된 링크 프리뷰가 도착해도 한 턴으로 묶고, 관계없는 즉시 메시지는 여전히 분리합니다. 페이슈 음성 답장에는 재생 전 길이를 표시해 상대가 오디오 길이를 미리 알 수 있습니다. Discord와 텔레그램은 반복 답장이나 세션 전환에서도 답이 원래 대화에 붙어 있도록 정리됐고, 완료된 답장이 중복으로 두 번 뜨던 문제도 함께 해결됐습니다.

배경 이미지·영상·음악처럼 오래 걸리는 작업 결과가 완료 후 원래 대화로 다시 돌아오도록 라우팅이 다듬어졌습니다. 텔레그램은 짧은 프리뷰나 진행 표시가 나가는 동안에도 "작업 중"임을 계속 알려 침묵 구간을 줄였고, 오래 붙잡혀 있던 메시지 한 건이 타임아웃돼도 이후 대화는 게이트웨이 재시작 없이 회복합니다.

### 모델과 프로바이더 복구력

프로바이더 쪽은 겉으로 잘 드러나지는 않지만, 실사용에서 자주 걸리던 지점을 여러 개 잡았습니다. MiniMax TTS는 이제 OpenClaw가 디코드 가능한 오디오 포맷을 명시적으로 요청해 실패율을 낮췄고, 게이트웨이 운영자는 기본 로그에서 프로바이더·모델·요청 상태·타이밍을 다시 볼 수 있습니다. 문제 진단을 위해 디버그 로그를 별도로 켜야 했던 부담이 줄어듭니다.

Google·Mistral·OpenAI Responses·Azure OpenAI Responses·ChatGPT/Codex Responses 경로에서 시스템 프롬프트에 OpenClaw 내부의 캐시 경계 마커가 그대로 실려 나가던 문제가 잡혔습니다. OpenAI 호환 프로바이더를 거쳐 Gemini를 쓰던 cron 툴 호출은 nullable 필드 때문에 스키마 거부가 나던 케이스가 정리됐고, 프로바이더가 붙은 모델 ID는 이제 설정된 런타임 정책과 CLI 별칭을 존중합니다. 채팅에서 `/models`를 열 때 CPU 코어를 몇 초씩 잡던 재스캔도 정상 속도로 돌아옵니다.

### 세션·메모리·신뢰의 연속성

에이전트 대화가 "성공은 했는데 답이 안 보인다"는 상황이 많이 줄었습니다. OpenAI Responses를 쓰는 대화가 저장된 히스토리가 불완전한 상태에서도 다음 턴부터 다시 정상 응답할 수 있고, Codex 백엔드가 아주 큰 툴 결과를 뱉어도 저장·재생 시 텍스트 크기를 기존 한도 안에서 유지합니다.

컨트롤 UI 대화는 슬립·네트워크 단절·게이트웨이 재접속 뒤에도 같은 세션에서 계속 이어집니다. 자동 컴팩션 중에 정지 버튼을 누르면 컴팩션 요청까지 함께 취소돼 컨텍스트가 날아가는 일이 줄고, 웹챗의 세션 상태·사고 레벨·토큰 컨텍스트·비용도 실제 사용 중인 대화 기준으로 표시됩니다.

### 새 기능: Slack 라우터 릴레이와 Raft 웨이크 브리지

기능 신규는 두 축입니다. Slack 라우터 릴레이 모드는 관리형·다중 게이트웨이 배포에서 Slack 트래픽을 중앙에서 받아 각 OpenClaw 게이트웨이로 라우팅하면서, 멘션·스레드·응답의 소유권은 원래 게이트웨이에 남겨둡니다. 게이트웨이 여러 대가 물려 있는 조직이라면 Slack 트래픽을 지금보다 훨씬 깔끔하게 정리할 수 있습니다.

Raft External Agent 웨이크 브리지는 로컬 CLI 진입점을 지원합니다. 워크스페이스에 밀린 작업이 있을 때 로컬 CLI로 OpenClaw 에이전트를 깨울 수 있고, 이름 붙은 프로파일과 CLI 사전 조건 점검도 함께 들어갔습니다. 짧지만 자동화 파이프라인에 붙이기 좋아졌습니다.

### 공식 플러그인 설치와 복구

플러그인 관리도 실사용 흐름에 가깝게 정비됐습니다. `plugins.allow`에 채널 이름이나 패키지 이름을 잘못 적으면 시작 시 어떤 항목이 안 맞고, 어떤 플러그인 ID로 고쳐야 하는지 안내가 뜹니다. 첫 설치 시 뜨는 신뢰 경고에는 복사·붙여넣기 가능한 `plugins.allow` 예시와 목록·조회 명령이 함께 나와 사용자가 스스로 해결할 수 있습니다.

`npm EOVERRIDE`로 실패하던 설치·업데이트는 오래된 관리형 의존성 pin을 자동 회복해 통과하고, 나중 동기화가 사용자가 명시적으로 설치한 패키지를 다운그레이드하거나 지우지 않습니다. `openclaw migrate`도 표준 글로벌 플러그인 설치를 인식해 Codex 마이그레이션이 "Unknown migration provider"에서 멈추지 않습니다.

### 게이트웨이 회복과 원격 결과 전달

`openclaw gateway probe --timeout ...`는 이제 설정한 시간까지 실제로 기다립니다. 내부 컷오프가 더 짧아서 "도달 불가"로 잘못 판정되던 문제가 사라졌습니다. 리눅스에서 메모리 압박으로 자식 프로세스가 종료돼도 systemd 관리형 게이트웨이는 살아남아 채널 연결을 유지하고, 실행을 취소하면 다음 모델 턴을 시작하지 않고 즉시 종료합니다.

원격 Codex 앱 서버에서 만든 이미지는 `Media failed`가 뜨거나 텍스트만 남는 대신 첨부로 정상 도착하고, 서브에이전트가 마쳤을 때 그 결과가 부모 실행으로 되돌아오는 경로도 안정화됐습니다.

## 실무자가 볼 핵심 포인트

운영자는 채널 라우팅 수정부터 확인하는 게 좋습니다. 그동안 "답이 다른 방으로 갔다", "그룹 컨텍스트가 깨졌다"는 리포트가 있었다면 6.11에서 상당 부분 정리됐을 가능성이 높습니다. 특히 텔레그램 인용 응답, 왓츠앱 그룹 답장, 구글 챗 DM 라우팅은 실제 사용 시나리오로 한 번 훑어보고 넘어가면 이후 지원 부담이 줄어듭니다.

프로바이더 로그 복구는 문제 진단에 바로 도움이 됩니다. 그동안 원인을 찾기 위해 별도 디버그 플래그를 켜야 했다면, 기본 로그만으로도 프로바이더·모델·요청 상태·타이밍을 다시 볼 수 있습니다. Gemini를 OpenAI 호환 경로로 쓰는 cron 작업이 있다면, 스키마 거부가 사라졌으니 별도 우회 로직을 제거할 수 있습니다.

컴팩션 중 정지 버튼이 컴팩션도 함께 취소한다는 점은 사용자 경험에서 큰 차이입니다. 컨텍스트가 사라지는 경험이 줄어들면 사용자가 정지 버튼을 조금 더 편하게 쓸 수 있습니다.

Slack을 여러 게이트웨이로 나눠 쓰는 조직이라면 새로 들어온 라우터 릴레이 모드를 검토해 볼 만합니다. 중앙 라우팅과 게이트웨이별 소유권을 함께 가져갈 수 있어, 지금 별도 프록시로 처리하던 트래픽을 정식 경로로 옮기는 선택지가 열렸습니다. Raft를 쓰는 팀이라면 로컬 CLI 웨이크 브리지로 자동화 파이프라인의 트리거 지점을 미리 정리해 두는 걸 권합니다. 이후 워크플로 설계가 한결 단순해집니다.
