지난 1년 사이 온톨로지 마케팅이 다시 강해졌습니다. LLM 환각의 해결책, 데이터 사일로의 종결자, 에이전틱 AI의 가드레일. 슬라이드는 이렇게 묶이고, 결론은 거의 늘 같습니다. “그래서 의미 인프라를 구축해야 합니다.”

이 글은 온톨로지를 깎아내리려는 글이 아닙니다. 온톨로지는 제자리가 분명한 기술이에요. 다만 마케팅 문장에서는 그 제자리보다 훨씬 넓은 문제를 풀 수 있는 것처럼 보일 때가 많습니다.

그래서 질문 하나만 짚고 갑니다.

> 지금 우리 회사에 필요한 게 정말 온톨로지인가요, 아니면 검색과 데이터 운영의 기본기를 먼저 정리해야 하는 상황인가요?

대부분의 일반 기업에서는 후자입니다. 결재 전에 확인해 둘 만한 기준 7가지를 정리했어요.

## 1. “RAG의 한계”는 보통 vectorDB 단독 사용의 한계예요

GraphRAG나 온톨로지 자료에는 비슷한 비교표가 자주 등장합니다. “기존 RAG는 벡터 유사도뿐이라 환각이 잦고 다단계 추론에 약하다”는 식이죠. 여기서 조심할 건 RAG = vectorDB로 슬쩍 좁혀 놓는다는 점입니다.

RAG는 외부 근거를 찾아 LLM 컨텍스트에 넣는 패턴이에요. 검색 backend는 vectorDB일 수도, BM25일 수도, SQL일 수도, graph DB일 수도 있어요. 운영 시스템에서는 BM25 + vector + metadata filter + reranker를 함께 쓰는 경우가 많습니다.

그러면 흔히 말하는 “기존 RAG의 한계” 중 상당수는 사실 “vectorDB만 단독으로 썼을 때의 한계”입니다.

예를 들어 사용자가 “구독 그만두려면요?”라고 물었다고 해볼게요. vector 검색만으로는 비슷한 표현은 잡지만 정확한 조항명이나 날짜 조건은 놓칠 수 있어요. 그렇다고 곧바로 온톨로지가 필요한 건 아닙니다. 보통 이런 순서로 먼저 보강합니다.

- BM25로 정확한 용어와 조항명을 잡고
- vector 검색으로 의역과 자연어 질문을 잡고
- metadata filter로 고객사·권한·날짜·문서 타입을 제한하고
- reranker로 후보 근거를 다시 정렬

이것도 RAG입니다. 온톨로지는 한 선택지일 뿐이에요. “RAG가 부족하니 온톨로지가 필요하다”는 한 칸 건너뛴 결론입니다.

## 2. vectorDB가 빠르게 자리잡은 이유를 짧게 넘기면 비교가 틀어집니다

온톨로지 자료는 vectorDB를 “유사도 검색” 정도로 가볍게 처리하곤 해요. 틀린 말은 아니지만, 왜 vectorDB가 빠르게 채택됐는지를 빼면 비교가 불공정해집니다.

vectorDB 이전에는 비정형 텍스트에서 의미를 찾는 방법이 꽤 고통스러웠습니다. 키워드 매칭만으로는 “두통, 어지러움” 검색이 “headache, dizziness”라고 적힌 노트를 못 잡아요. 동의어 사전을 직접 만들어야 했고, 그 사전은 도메인이 바뀌면 계속 손봐야 했습니다. 사람이 코드를 붙이는 방식도 마찬가지였어요. 입력 누락이 생기고, 사람마다 기준이 달랐죠.

vectorDB는 이 두 길을 우회했습니다. 사전 합의 없이도 의미가 가까운 문서를 찾을 수 있게 했어요. 한국어 질문으로 영어 문서를 잡고, 의역을 잡고, “계약 종료”와 “서비스 해지”처럼 부서마다 다르게 쓰는 표현도 어느 정도 묶어줍니다.

이게 결정적이었습니다. 도메인 전문가 워크숍을 열고 분류 체계를 합의하기 전에, 원문을 넣고 검색을 돌릴 수 있게 된 거예요. 정직한 비교는 이래야 합니다.

> vectorDB는 비정형 텍스트의 넓은 부분을 빠르게 열어줍니다. 온톨로지는 합의 가능한 좁은 부분을 더 엄밀하게 다룹니다.

둘은 적이 아닙니다. 문제는 순서예요. 넓은 검색 문제를 풀지 못한 상태에서 처음부터 전사 온톨로지를 만들겠다고 들어가면 비용이 먼저 커집니다.

## 3. 온톨로지가 빛나는 영역은 좁고 분명합니다

온톨로지가 ROI를 내는 곳은 정해져 있어요.

- 유전자 기능 분류처럼 학계 합의가 강한 영역
- 약물 상호작용처럼 닫힌 룰셋이 중요한 영역
- ICD, KCD, HS 코드처럼 행정과 규제가 합의를 강제하는 영역
- 도서관 분류나 통제 어휘처럼 합의 자체가 업무인 영역

공통점이 있습니다. 합의를 만드는 비용보다 합의가 주는 이익이 큽니다. 그리고 많은 경우 그 합의는 이미 만들어져 있어요. 우리는 재사용만 하면 됩니다.

일반 회사 내부 데이터는 다릅니다. 영업팀이 말하는 customer, 마케팅팀이 말하는 customer, 회계팀이 말하는 customer가 다 다를 수 있어요. 영업팀에는 아직 계약 전인 리드도 customer처럼 보이고, 회계팀에는 청구가 시작된 계정만 customer일 수 있습니다.

이건 데이터 품질이 나쁜 게 아니라 의사결정 맥락이 다른 겁니다. 그걸 무조건 하나의 정의로 고정하려고 하면 프로젝트가 곧 조직 합의 프로젝트가 돼요. 데이터 인프라 구매가 아니라 변경관리·거버넌스 프로젝트가 되는 거죠.

흔한 흐름은 이렇습니다.

- 1개월 차: 클래스 초안이 나오고, 각 부서가 “우리는 그렇게 안 부릅니다”라고 말하기 시작
- 3개월 차: 큰 합의는 미뤄지고 작은 정의만 늘어남
- 6개월 차: 일부 매핑은 끝나지만 기존 시스템 연결이 남음
- 9개월 차: 새 시스템 도입과 변경관리 이슈 발생
- 12개월 차: 관리되지 않는 .ttl 파일과, 잘 열리지 않는 거버넌스 회의

특정 벤더가 나빠서가 아니에요. 합의되지 않은 도메인에 합의된 모델을 먼저 씌울 때 자연스럽게 생기는 비용입니다.

## 4. 의미가 시간에 따라 바뀌는 데이터에는 잘 안 맞아요

마케팅 데모는 깔끔합니다. “고객 A가 제품 B를 구매했다” 같은 트리플이죠. 실제 업무 데이터는 시간이 지나면서 의미가 바뀝니다.

고객지원 사례 하나만 볼게요.

- 1일 차: 사용자가 “로그인이 안 됩니다” 문의
- 1일 차 오후: 상담사가 비밀번호 재설정 이슈로 분류
- 2일 차: 엔지니어가 OAuth callback 설정 문제로 봄
- 3일 차: 보안팀이 의심 IP 패턴을 보고 계정 보호 이슈로 재분류
- 5일 차: 고객 성공팀이 엔터프라이즈 온보딩 실패 사례로 기록

같은 티켓인데 관점이 계속 바뀝니다. 처음에는 인증 문제였고, 다음에는 설정 문제였고, 나중에는 보안 이벤트이자 온보딩 리스크가 됩니다. 어느 하나가 완전히 틀렸다기보다 시간과 역할에 따라 설명 레이어가 달라진 거예요.

이걸 OWL 스타일의 엄밀한 온톨로지로 모델링하려면 곧 복잡해져요. 상태(suspected, confirmed, superseded), 시간(과거 판단의 변경), 의견 충돌, 재해석을 다 담아야 합니다. 이론적으로는 가능해요. 다만 그 순간 모델은 커지고, 운영 규칙은 복잡해지고, 사람들은 입력을 피하기 시작합니다. 결국 사용자는 그래프 탐색 화면이 아니라 검색창으로 돌아옵니다.

> 온톨로지는 의미 합의를 기록 시점에 고정하는 데 강합니다. 많은 실무 데이터는 합의가 질의 시점에 다시 만들어집니다.

vectorDB + LLM 방식은 이 합의를 질의 시점으로 미룹니다. “이 고객의 로그인 이슈가 왜 보안 이벤트로 바뀌었나요?”라고 물으면, 티켓·로그·Slack·CRM 노트를 시간순으로 모아 LLM이 근거와 함께 설명해줘요. 원문 의견이 살아 있으니 관점 차이도 같이 보여줄 수 있고요.

## 5. “온톨로지로 만들었다”는 말, 실제로는 사전인 경우가 많아요

가장 깊은 혼동은 여기서 생깁니다.

“우리 회사 데이터를 온톨로지로 정리했습니다.”
“AI 소설 세계관을 온톨로지로 만들었습니다.”
“제품 카탈로그를 온톨로지로 구조화했습니다.”

세 문장이 가리키는 게 다 다를 수 있어요. 많은 경우 진짜 온톨로지라기보다 내부 사전, 세계관 사전, 인스턴스 그래프에 가깝습니다.

온톨로지의 본질은 한 단계 위의 분류 체계입니다. “이 도메인에 어떤 종류의 것들이 존재할 수 있고, 어떤 관계가 가능한가”를 정의하는 모델이에요.

창작 예시로 보면 이렇습니다. “칼레브는 마법사이고 라엘의 스승이다”는 훌륭한 세계관 사전입니다. 그래프로 그릴 수도 있어요. 하지만 보통 온톨로지는 아닙니다. 그 작품 안에서만 통하는 사실이니까요. 진짜 온톨로지에 가까운 건 한 단계 위입니다. 판타지 캐릭터 유형(마법사·전사·치유자·암살자), 마법 시스템 유형(원소·룬·계약·기억), 서사 구조 유형(3막·영웅의 여정·옴니버스) — 다른 작가, 다른 작품에도 재사용될 수 있는 분류죠.

기업 데이터도 같습니다.

- “우리 고객은 245만 명입니다” — 인스턴스 사실
- “우리 회사에서는 가입 후 첫 결제까지 한 사람을 customer로 부릅니다” — 내부 정의
- 부서별 정의를 모은 문서 — internal glossary 또는 data dictionary

다른 회사·시스템이 그대로 받아 쓸 수 있는 분류 체계라면 온톨로지에 가깝습니다. 한 조직 안에서만 통하면 사전이에요. 시금석은 재사용 가능성입니다.

> 한 조직 안에서만 통하면 internal glossary에 가까워요. 온톨로지라는 이름보다 “재사용 가능한 분류 체계인가”를 먼저 봅니다.

그리고 하나 더. 온톨로지는 graph DB와도 다른 층입니다. SNOMED CT는 RF2 포맷으로 배포되고 병원 시스템에서는 RDB에 적재되는 경우가 많아요. schema.org는 JSON-LD나 microdata로 웹 페이지에 들어갑니다. HL7 FHIR는 JSON과 REST API로 운영돼요. 회계 계정과목은 ERP의 RDB에 살고요. 그래프 DB에 저장하지 않아도 도메인 모델은 존재합니다. 반대로 Neo4j에 노드를 넣었다고 자동으로 온톨로지가 생기는 것도 아니에요. 그래프 DB는 저장소, 온톨로지는 모델입니다.

## 6. 그래프 데모는 멋지지만 결재 근거가 되어선 안 돼요

그래프 데모는 강합니다. 가운데 고객 노드가 있고, 제품·계약·티켓·문서·담당자가 빛처럼 연결됩니다. 클러스터는 색깔별로 나뉘고, 마우스를 올리면 노드가 움직이죠. 임원 회의에서 이런 화면은 설득력이 있어요.

반대로 embedding 공간을 UMAP으로 보여주면 감탄이 덜합니다. 점들의 군집은 분석가에게는 의미 있지만, 결재자에게는 그냥 점처럼 보일 수 있어요.

이 미적 차이가 의사결정에 영향을 줍니다. 그래서 더 조심해야 해요.

운영에서는 그래프 시각화가 생각보다 빨리 한계에 부딪힙니다. 100개 노드를 넘으면 화면이 복잡해지는데 실제 시스템은 수만에서 수백만 노드입니다. 사용자는 대개 그래프를 직접 보지 않아요. 검색 결과, 답변, 알림, 업무 화면을 봅니다. 실제 query는 1~2 hop인 경우가 많고, 이 정도는 SQL JOIN과 metadata filter로도 충분해요. 모든 게 “회사”·“고객”·“문서” 같은 hub node에 연결되면 traversal 결과가 금세 넓어지기까지 합니다.

그래프가 필요 없다는 뜻은 아닙니다. 사기 탐지, 자금세탁, 권한 전파, 공급망 리스크처럼 깊은 관계 탐색이 비즈니스 로직인 영역에서는 강해요. 다만 “그래프가 멋있다”와 “우리 운영 문제의 최선 해결책이다”는 다른 문장입니다.

## 7. 그럼 진짜 온톨로지가 필요한 회사는?

분명히 있어요. 다만 범위는 좁습니다.

- 분류 자체가 제품인 회사 — 의약품 DB, 화학물질 카탈로그, 생물학 표준 어휘
- 규제 보고나 청구 코드가 핵심인 회사 — ICD, KCD, FHIR, HS 코드처럼 외부 표준이 이미 있음
- 닫힌 룰셋 추론이 핵심인 시스템 — 다만 OWL보다 SHACL·룰 엔진·RDB constraint가 더 실용적인 경우가 많음
- 제품 카탈로그 SEO가 중요한 커머스 — schema.org 재사용
- 관계 탐색 자체가 제품 가치인 영역 — 사기 탐지, 자금세탁 탐지, 소셜 네트워크, 권한 전파

이 범위에 들어간다면 온톨로지나 graph 설계가 좋은 선택일 수 있어요. 단, 순서는 같습니다. 산업 표준이 있는지 먼저 확인하고, 있으면 재사용하고, 부족한 부분만 작게 확장합니다.

반대로 일반 기업 지식검색, 사내 문서 QA, 고객지원 assistant, 영업 enablement, 정책 검색 같은 문제라면 대부분 hybrid RAG부터 시작하는 편이 맞아요.

## 결재 전에 던질 7가지 질문

다음 미팅에서 슬라이드가 넘어갈 때 던져볼 만한 질문입니다. 공격적인 질문이 아니라 범위를 맞추는 질문이에요.

1. “기존 RAG의 한계”라고 하신 건 vectorDB 단독 한계인가요, BM25 + vector hybrid까지 포함한 한계인가요?
2. 인용하신 GraphRAG 사례가 OWL 추론을 썼나요, 아니면 property graph + LLM extraction인가요?
3. 우리 도메인에 이미 재사용 가능한 표준이 있나요, 아니면 조직 합의를 새로 만들어야 하나요?
4. 우리가 만들 결과물은 다른 회사·외부 시스템도 재사용할 수 있나요, internal glossary인가요?
5. graph DB가 정말 최선의 저장소인가요? RDB·JSON-LD·FHIR API·search index가 더 적합하지 않은 이유는요?
6. 첫 사용자가 결과를 보기까지 며칠이 걸리나요?
7. 구축 후 누가 정의·매핑·룰 변경을 승인하고 운영하나요?

답이 흔들리는 항목이 있다면 프로젝트를 사지 말라는 뜻이 아닙니다. 범위를 줄여야 한다는 뜻이에요. “전사 온톨로지”가 아니라 “청구 코드 매핑 schema”, “제품 카탈로그 schema.org 확장”, “고객지원 티켓 graph 탐색”처럼 이름을 작게 바꾸면 됩니다.

## 먼저 할 일은 더 작고 지루합니다

대부분의 회사가 지금 해야 할 일은 더 작고 덜 화려해요.

- 원문 문서를 잃지 않게 저장
- 권한과 tenant boundary를 검색 단계에서 강제
- BM25 + vector + metadata filter 조합으로 검색
- reranker로 근거 후보 정리
- 정답 세트를 만들어 검색 품질 측정
- 사용 로그에서 실패한 질문 수집
- 합의가 반복해서 필요한 좁은 영역만 schema로 승격

이 순서가 맞습니다. 처음부터 모든 의미를 고정하려 하지 마세요. 의미가 안정적으로 반복되는 곳이 보일 때만 그 부분을 모델로 올리면 됩니다.

## 정리

온톨로지는 좋은 도구입니다. 다만 모든 데이터 문제의 출발점은 아니에요. 특히 AI 시대에는 “의미를 미리 완전히 합의한다”보다 “원문을 보존하고, 검색으로 근거를 모으고, 질의 시점에 설명한다”가 더 빨리 작동하는 경우가 많아요.

> 의미는 합의로 고정되기 전에 검색으로 잘 보존되어야 합니다. 합의는 그 다음입니다.

기억할 한 줄은 이거예요. **온톨로지를 살까 고민된다면 먼저 RAG 기본기부터 점검하세요.** 그래도 부족한 게 명확해진다면 그때 좁은 schema 한 조각만 작게 시작하면 됩니다.
