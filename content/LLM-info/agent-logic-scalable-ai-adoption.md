LLM을 더 크게 만들면 기업 AI 도입도 자연스럽게 풀릴까요. IBM Research가 Hugging Face에 공개한 글은 그 답을 꽤 분명하게 나눕니다. 모델 자체보다 중요한 것은 모델이 업무 흐름을 벗어나지 않게 붙잡아 주는 **Agent Logic**입니다.

## 핵심 요약

- IBM Research는 기업 AI 확산의 핵심을 LLM 크기보다 **업무를 안내하는 agent logic**에서 찾습니다.
- Agent Logic은 지식그래프, 프로그램 분석 라이브러리, 알고리즘, 정책-as-code처럼 에이전트 계층에서 LLM의 탐색 범위를 줄이는 소프트웨어 구조입니다.
- IBM은 레거시 코드 이해, 테스트 생성, 장애 원인 분석, 컴플라이언스 자동화에서 토큰 사용량을 줄이면서 성능을 높인 사례를 제시했습니다.
- regulated enterprise 환경에서는 “모델이 자율적으로 추론하되, 권한과 실행은 정책이 제어한다”는 구분이 중요합니다.
- 기업이 AI 에이전트를 도입할 때는 프롬프트보다 데이터 구조, 도구 권한, 검증 루프, 정책 레이어를 먼저 설계해야 합니다.

## Agent Logic은 무엇인가

IBM은 Agent Logic을 에이전트 하네스 안에서 동작하는 소프트웨어 원시 요소로 설명합니다. 지식그래프, 알고리즘, 프로그램 분석 라이브러리, 정책 규칙 같은 것들이 여기에 들어갑니다.

핵심은 LLM에게 모든 맥락을 한 번에 밀어 넣는 대신, 에이전트가 봐야 할 범위를 미리 좁혀 주는 데 있습니다. 기업 업무는 보통 오래 걸리고, 여러 API와 데이터베이스를 건너며, 규정이나 내부 정책의 제약을 받습니다. 이런 흐름을 LLM 하나에 모두 맡기면 컨텍스트는 커지고, 비용은 늘고, 답변의 일관성도 흔들리기 쉽습니다.

Agent Logic은 여기서 내비게이션 역할을 합니다. 모델이 “아무 자료나 넓게 읽는” 대신 “지금 업무 단계에 필요한 근거와 규칙만 좁게 보는” 구조를 만드는 것입니다.

## 왜 기업 워크플로에는 LLM 단독 접근이 흔들리나

IBM이 짚은 기업 워크플로의 특징은 세 가지입니다.

첫째, 동적이고 오래 지속됩니다. 장애 대응, 컴플라이언스 점검, 레거시 시스템 현대화 같은 일은 한 번의 답변으로 끝나지 않습니다. 상태가 바뀌고, 중간 결과를 다시 확인해야 합니다.

둘째, 연결된 시스템이 많습니다. 코드 저장소, 관측 데이터, 티켓, 정책 문서, 고객 환경, 내부 승인 절차가 함께 움직입니다. LLM이 전체를 한꺼번에 읽는 방식은 금세 비싸지고 느려집니다.

셋째, 규정과 정책이 강하게 작동합니다. 특히 금융, 의료, 공공, 대기업 IT 운영에서는 “그럴듯한 답”보다 “허용된 절차 안에서 나온 추적 가능한 답”이 중요합니다.

그래서 IBM의 메시지는 단순합니다. LLM을 업무 중심에 놓으려면 더 큰 모델만 고를 게 아니라, 모델 주변에 구조화된 안내 장치를 붙여야 합니다.

## IBM 사례에서 보이는 세 가지 패턴

IBM은 여러 제품과 연구 사례를 통해 Agent Logic의 효과를 설명합니다. 숫자 하나하나보다 중요한 것은 반복되는 패턴입니다.

### 1. 프로그램 분석으로 코드 이해 범위를 좁힌다

레거시 코드 이해와 테스트 생성 사례에서는 프로그램 분석이 핵심 역할을 합니다. IBM watsonx Code Assistant for Z의 App Insights agent는 대규모 레거시 애플리케이션을 미리 분석해 구조화된 표현으로 저장합니다. 그 결과 LLM은 전체 코드를 매번 읽지 않고, 이미 정리된 정보를 찾아 사용합니다.

IBM은 최대 100만 줄 코드와 1천 개 프로그램 규모의 시스템에서, LLM-only 기준보다 비슷하거나 더 나은 이해 성능을 유지하면서 토큰 사용량을 크게 줄였다고 설명합니다. 테스트 생성 도구 Aster에서도 프로그램 분석 결과를 프롬프트와 하위 에이전트에 연결해 커버리지 개선과 비용 절감을 함께 노렸습니다.

### 2. 지식그래프로 장애 원인 분석을 국소화한다

운영 환경에서는 코드만 보는 것으로 부족합니다. 마이크로서비스, 데이터베이스, 미들웨어, 로그와 메트릭, 팀이 알고 있는 암묵지까지 함께 봐야 합니다.

IBM은 여기서 지식그래프를 사용합니다. 전체 IT 스택을 무작정 LLM 컨텍스트에 넣는 것이 아니라, 관측 데이터와 그래프 구조를 바탕으로 관련된 근거만 좁혀 갑니다. Instana의 intelligent incident investigation 사례와 ITBench 평가 결과에서도 이런 “국소 추론” 접근이 ReAct식 일반 에이전트보다 더 안정적으로 작동했습니다.

### 3. 정책과 알고리즘으로 에이전트 권한을 제한한다

컴플라이언스 자동화와 의료 고객 케어 사례에서는 정책 기반 제어가 더 중요해집니다. IBM은 policy-as-code와 adaptive planning을 통해 에이전트가 무엇을 말하고, 어떤 도구를 쓰고, 언제 사람에게 넘겨야 하는지를 런타임에서 제한합니다.

이 관점은 실무적으로 중요합니다. 에이전트가 자율적으로 추론하는 것과, 에이전트에게 최종 권한을 주는 것은 다릅니다. 기업 환경에서는 추론은 자동화하되 권한은 정책과 감사 체계가 잡아야 합니다.

## 도메인 사례가 던지는 메시지

IBM 글에서 흥미로운 대목은 순수 IT 운영 사례를 넘어 의료와 설비 관리까지 같은 논리를 확장한다는 점입니다.

의료 보험 고객 응대 예시로 소개된 CUGA(Configurable Generalist Agent)는 모델을 새로 학습시키기보다, 런타임 정책 시스템으로 안전한 의도 처리와 도구 사용, 출력 형식을 강제합니다. IBM은 Claude Opus 4.5, GPT OSS 120B, GPT-4.1 계열을 놓고 실험했을 때 정책 시스템이 task correctness 격차를 줄였다고 설명합니다. 여기서 중요한 포인트는 모델 계열이 바뀌어도 정책 레이어가 별도로 남는다는 점입니다.

물리 자산 유지보수 사례도 비슷합니다. IBM Global Real Estate 환경에서 Maximo Condition Insights agent는 센서, 작업 지시, 고장 유형, 이벤트 분석을 함께 묶어 설비 상태를 판단합니다. AssetOpsBench 기준으로 unsupported claim을 줄이고, 평균 토큰 사용량도 낮췄다는 설명이 붙어 있습니다. 단순히 “LLM이 보고서를 잘 쓴다”가 아니라, 어떤 증거를 어떤 순서로 확인할지 구조화했다는 쪽에 무게가 있습니다.

이 두 사례는 Agent Logic을 좁게 IT 자동화 도구로만 볼 필요가 없다는 점을 보여줍니다. 규정이 강한 고객 응대, 물리 장비 점검, 컴플라이언스 운영처럼 결과를 설명해야 하는 업무일수록 모델 바깥의 구조가 더 중요해집니다.

## 실무자가 볼 핵심 포인트

기업이 AI 에이전트를 도입할 때 바로 적용할 수 있는 기준은 다음과 같습니다.

1. LLM 컨텍스트를 키우기 전에 검색 범위를 줄일 구조가 있는지 확인합니다.
2. 반복되는 업무에는 프로그램 분석, 지식그래프, 룰 엔진, 정책-as-code 중 어떤 안내 장치가 맞는지 먼저 고릅니다.
3. “모델이 알아서 하게 한다”가 아니라 “모델이 볼 근거와 쓸 도구를 제한한다”는 관점으로 설계합니다.
4. 성능만 보지 말고 토큰 사용량, 재시도 횟수, 사람이 검토해야 하는 비율을 함께 측정합니다.
5. regulated workflow에서는 답변 품질보다 권한, 감사 가능성, 근거 추적성이 먼저입니다.

한 줄로 정리하면 이렇습니다.

> 기업 AI 에이전트의 품질은 모델의 크기만으로 정해지지 않습니다. 모델이 업무 안에서 길을 잃지 않게 만드는 구조가 품질과 비용을 함께 좌우합니다.

Agent Logic이라는 표현은 새로워 보이지만, 실무 관점에서는 꽤 익숙한 원칙입니다. 좋은 자동화는 항상 맥락을 좁히고, 권한을 제한하고, 검증 가능한 근거를 남깁니다. LLM 시대의 기업 AI도 결국 이 기본기를 다시 요구합니다.
